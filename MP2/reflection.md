# Reflection

## What did you build?

I built AccessiPair, which is an interactive Streamlit app that helps HCD students, UI designers, and product designers make more accessible color pairing decisions in their UI or design work. The app supports entering custom HEX colors, importing pasted palette text, auditing foreground/background combinations, calculating WCAG contrast ratios, generating accessible repair recommendations, previewing pairings in UI components, and saving useful pairs. The intended flow is that a user enters or imports their HEX codes, checks to see if the color pairing passes WCAG's guidelines and ratios for accessible color pairing, and can either 'repair' the color pairing by changing the colors to a more accessible contrast or send the already accessible color pairing to the component lab where users can view what their color pairing would look like on various UI components (like buttons, badges, cards, etc). Users can also save their accessible color pairings for later use. If users import the HEX codes of an existing color palette, the app will also automatically try every possible color pairing within the palette and tell users which pairings are accessible and ready to use or which pairings would need 'repair' or cannot be used. The recommended changes to color pairings also try to stay in the general color range of the user's original color, and the app instead tries to change only saturation and hue rather than color (when possible). The app also gives other recommendations which preserve text color or preserve background color, because sometimes designers are made to use a certain color due to existing brand guidelines. These were all intentional choices, because sometimes designers have constraints but still require helpful guidance and possible recommendations for color pairings. 

The goal was to move beyond a basic contrast checker. A simple checker can tell a designer that a pair's WCAG ratio is `3.2:1`, but that does not always explain what the number means, whether it is acceptable for a specific UI use, or what to do next. AccessiPair tries to connect the full workflow so users can import colors, find weak pairings, repair failed pairs, preview the result in interface components, and save combinations that are useful later.

This came from a real design frustration for me. In UX and HCD work, a designer might be working with brand colors, Figma tokens, course project mockups, or a design system that already has a visual direction. When a color pair fails contrast, the useful answer is not only "use black" or "use white." The useful answer is closer to: "Here is the smallest change that preserves the palette, here is the safer readability fallback, and here is what that choice looks like in a button, badge, form field, or card." That is the kind of decision support I wanted AccessiPair to provide.

## What decisions did you make?

My original MP2a declaration said I would build the project in Bolt. I chose Bolt because it was recommended as one of the options for the assignment and seemed appropriate for an interactive tool with visual UI and some computation. I started there, but Bolt became a problem as the project got more complex. I ran into credit limits, and the generated app stayed too basic. It could produce a static visual interface, but it struggled to connect features into a coherent app workflow.

I also used ChatGPT to think through the contrast logic, recommendation strategies, and app structure. ChatGPT helped me reason about features and generate pieces of code, but manually inserting code into Bolt still did not solve the full usability problem. The app still felt disconnected and the palette audit, pair repair, component preview, and saved pairings did not feel like one workflow. This was a good reminder that generating working code and designing a usable product are related but not the same thing. A page can technically function and still leave a first time user wondering, "Where did this color pair come from?" or "What am I supposed to click next?"

I eventually switched to Codex because the project needed connected feature logic across multiple pages and more control over a larger codebase. I chose Streamlit/Python for the final version because it made the contrast math, palette parsing, state management, and deployment path more manageable. Streamlit also let me keep everything client side without authentication, a backend or a database.

I chose paste/import for Figma/CSS colors instead of real Figma API integration. That felt more realistic for the scope of this project and still matched a real designer workflow of copying design tokens, CSS variables, or notes into a tool. It also kept the project focused on the accessibility decision rather than account setup, authentication, or API permissions. I also scoped the recommendation logic around preserving palette intent when possible. Instead of always jumping to black or white, AccessiPair tries strategies like balanced repair, preserving the surface, preserving the text color, and maximum readability.

Another important decision was to treat the app itself as part of the accessibility argument. Because AccessiPair is about readable UI color pairings, the interface needed clear hierarchy, strong button states, visible pass/fail labels, and plain-language explanations of the 3:1, 4.5:1, and 7:1 targets. I had to keep returning to the user experience, not just the contrast formula.

## What would you do differently?

The app’s strength is that it became more than a basic contrast checker. It tries to preserve palette intent and connect the decision-making process from audit to repair to preview to saving. But the feature set also became complex. As I added palette audit, custom pair testing, recommendation cards, component previews, and saved pairings, the flow became harder to make simple.

Bolt, ChatGPT, and Codex all helped at different points, but they also struggled in different ways. Bolt was useful for quick visual starting points but hit credit limits and did not handle the larger workflow well. ChatGPT was helpful for reasoning, but generated pieces did not automatically become a coherent app. Codex was better for working across the codebase, but adding more prompt context did not always improve usability, sometimes it created more features or more explanatory text instead of a clearer flow.

If I did this again, I would focus on fewer features in more depth. I might build only palette audit, failed-pair repair, and component preview, then make those three parts extremely clear before adding saved pairings or more recommendation options. For example, I would spend more time on the moment when a user selects a failed palette pair and moves into repair mode. That transition is the heart of the tool, so it should feel almost impossible to miss what happened, what failed, and what AccessiPair recommends next.

I think I got too excited about the full user workflow and ended up giving the AI tools more than they could handle. There are still some parts or features of the app that could be redesigned to be more usable or intuitive. So, I think I would definitely focus on quality of features rather than quantity next time. Due to this shortcoming, there's also some app errors that still come up even after multiple iterations with AI tools, like when you select importing a color palette it will show an error because we're not importing anything for real. The scope would have gotten too large by incoporating that Figma feature or APIs, so that was another shortcoming that I would eliminate altogether for this project, simply to fit within a realistic scope for this project. 

## What does this work demonstrate?

This project demonstrates **C1 — Vibecoding and Rapid Prototyping** because I used AI tools (Bolt, ChatGPT, and Codex) to move from a plain language concept to a working app, then iterated when the first platform was not enough. I started with Bolt, used ChatGPT to reason through features, and switched to Codex when the project needed more control and connected logic across app features.

It demonstrates **C2 — Code Literacy and Documentation** because I revised a Python/Streamlit app and added plain English inline comments in `app.py` so someone outside the course can understand the project. The comments explain the parts of the code that matter most for the tool: HEX validation, RGB conversion, luminance, contrast ratio calculation, target checking, palette import, repair generation, session state, and saved pairings. This was done so that either myself or anyone else reading the code file would be able to understand how the app does accessible color pairing checks, the main functions and the logic/reasoning behind them. 

It demonstrates **C7 — Critical Evaluation and Professional Judgment** because I did not accept the AI-generated output as automatically good. Early versions technically worked but they were often static screens or felt like disconnected contrast checking pages. I had to decide that the problem was not just code correctness but also the usability and user workflow clarity. I also had to recognize when more prompting was making the app busier instead of clearer. I attempted to fix this by changing AI tools when needed, and supplementing Codex with proper context and goals/outcomes needed for the app features.

It demonstrates **C8 — Building and Deploying a Complete Tool** because AccessiPair is a complete interactive tool for a real HCD use case. It helps designers make accessible color decisions by importing colors, auditing combinations, repairing failed pairs, previewing results as common UI components, and saving pairings. The biggest challenge was connecting those features into a tool that someone could actually use during a design workflow, and not just proving that the contrast math works like in a normal color auditing tool.
